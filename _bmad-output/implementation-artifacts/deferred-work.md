## Deferred from: code review of 4-4-post-completion-customer-rating (2026-05-18)

- **`averageRatingCache` / `ratingsCountCache` never updated**: `HandymanProfile` has these nullable cache fields but `RatingsService.submitRating` never updates them after creating a rating. Any feature reading reputation data will always see null. Address when a ratings aggregation feature is built (`apps/backend/src/modules/ratings/ratings.service.ts`).
- **`RatingStatusResponseSchema` not a discriminated union**: `stars` can theoretically be non-null when `hasRating: false` due to a logic error or partial write. A Zod `z.discriminatedUnion` would make the contract precise. Low risk in practice with existing service guards; defer to contracts hardening (`packages/contracts/src/rating.schemas.ts`).
- **`handymanId` snapshot drift**: Rating records the `assignedHandymanId` at submit time without a DB lock on the request row. Future handyman-reassignment scenarios (even if not in MVP) could attribute the rating to the wrong handyman. Address if reassignment is ever added (`apps/backend/src/modules/ratings/ratings.service.ts:40`).
- **Missing indexes on `request_ratings.customer_id` and `handyman_id`**: Profile-level aggregation queries (e.g., "all ratings given by customer X" or "all ratings received by handyman Y") will full-scan `request_ratings`. Add `@@index([customerId])` and `@@index([handymanId])` in Epic 5 schema hardening (`apps/backend/prisma/schema.prisma`).
- **Submit button double-fire race**: Two rapid taps before `isPending` propagates could fire two POST requests simultaneously. Server-side P2002 handling (patch in this review) prevents DB corruption, but two 400 responses may confuse the user. Debounce or disable-on-click-until-response pattern recommended if tap testing reveals this in practice (`apps/frontend/src/features/request-rating/components/RatingPromptSheet.tsx:86`).
- **`getRatingStatus` does not validate request `status`**: Endpoint returns valid 200 for non-COMPLETE requests. Frontend gates on `isComplete`, so this is acceptable for MVP. Consider returning 409 Conflict for non-COMPLETE requests to make the contract self-documenting (`apps/backend/src/modules/ratings/ratings.service.ts:55`).
- **`SubmitRatingResponseSchema.stars` unconstrained**: Response schema uses `z.number()` without `.int().min(1).max(5)`. Low risk — backend DTO prevents invalid values — but the contract is looser than the request schema. Tighten in a contracts-consistency pass.
- **Future terminal statuses not handled in `RequestCard`**: Adding a `CANCELLED` or `EXPIRED` lifecycle state to the backend would silently render as a non-linked plain div. Enumerate all terminal states explicitly when new statuses are introduced (`apps/frontend/src/features/customer-dashboard/components/RequestCard.tsx`).

## Deferred from: code review of 4-3-real-time-status-push-via-websocket (2026-05-18)

- **JWT_SECRET undefined allows silent verify**: `ConfigService.get('JWT_SECRET')` returning `undefined` may not cause `jwtService.verify()` to throw depending on JwtModule defaults, potentially allowing unauthenticated sockets. Pre-existing; startup `validate()` in ConfigModule catches missing env vars. Address in Epic 5 security baselines (`apps/backend/src/modules/realtime/realtime.gateway.ts:40`).
- **emitStatusUpdate on uninitialized gateway server**: `@WebSocketServer() server` is `undefined` before gateway bootstraps; calling `emitStatusUpdate` before bootstrap would crash. Pre-existing NestJS lifecycle concern; HTTP requests cannot arrive before server is fully started. Note for future startup-hook or early-init patterns.
- **CORS wildcard on WebSocket gateway**: `cors: { origin: '*' }` allows any origin to connect. Matches existing REST `enableCors()` approach. Tighten to known frontend origin(s) in production deployment (Epic 5 security baselines, `apps/backend/src/modules/realtime/realtime.gateway.ts:16`).
- **trackingQueryKey missing from useEffect deps**: Captured in closure but excluded from `[requestId, queryClient]` deps. Stable in practice (key derived from requestId which is in deps). If caller passes a variable key in future, silent stale-closure bug. Add to lint rules or document the constraint (`apps/frontend/src/features/shared/hooks/useJobStatusSocket.ts:65`).
- **Stale auth token across socket reconnect**: `getAccessToken()` called once at mount; socket auth token is not refreshed for the lifetime of the socket. On token expiry, reconnect attempts fail silently until server disconnects. Cross-cutting auth concern; existing logout flow handles re-login. Revisit when silent token refresh is implemented.
- **No navigate-to-login after server-forced disconnect**: `clearAccessToken()` is called on `'io server disconnect'` but no routing to `/login`. User sees frozen status display until next auth-required REST call fails and existing auth context redirects. Acceptable for MVP; improve UX in Epic 5 polish.
- **canAccessRoom: no rate limiting on join-room spam**: Authenticated socket can emit `join-room` in a tight loop, each triggering a `findUnique` DB query. No debounce, no per-socket join-rate limit. Platform rate limiting is Epic 5 / `5-2-apply-security-baselines` scope (`apps/backend/src/modules/realtime/realtime.gateway.ts:79`).
- **emitStatusUpdate fire-and-forget: missed push if process crashes between transaction commit and emit**: Status change is durably persisted but WS push never sent. Since polling is now disabled (`refetchInterval: false`), the client misses the update until the next window-focus refetch (which was itself noted as a separate concern). Spec-intentional fire-and-forget design; acceptable for MVP.

Add `handymanId: request.assignedHandymanId` to the findFirst `where` clause when hardening in Epic 5 (`apps/backend/src/modules/requests/requests.service.ts`).
- `refetchInterval: 30_000` runs unconditionally — polling continues for COMPLETE and REJECTED requests wasting bandwidth. Gate refetchInterval on active-lifecycle statuses or stop polling when status reaches a terminal state. Revisit in Epic 5 / story 4.3 when WebSocket push replaces polling (`apps/frontend/src/features/request-tracking/hooks/useRequestTracking.ts`).
- `request.category.name` accessed without null guard — if a ServiceRequest's category FK is somehow null (data corruption, future soft-delete), the tracking endpoint will crash with an unhandled TypeError. Add a null guard and fallback string when next touching this service method (`apps/backend/src/modules/requests/requests.service.ts`).
- `containerRef.current!` non-null assertion in MapLibre constructor — fast unmount or React Strict Mode double-invoke could pass null to the constructor. Add a `if (!containerRef.current) return;` guard at the top of the useEffect if map crashes are observed in development (`apps/frontend/src/features/request-tracking/components/RequestTrackingMap.tsx`).
- ON DELETE RESTRICT on `handyman_location_updates` FKs — consistent with all other project FKs; revisit when request cancel/delete flows are designed and decide between RESTRICT (manual cleanup) or CASCADE (auto-delete location rows) (`apps/backend/prisma/migrations/20260518120000_add_handyman_location_updates/migration.sql`).

## Deferred from: code review of 4-2-handyman-active-job-mode-with-status-updates-and-location-posting (2026-05-18)

- Race condition in `updateJobStatus` — `findUnique` + `$transaction` not atomic; two concurrent PATCH requests can both pass the `VALID_TRANSITIONS` check and double-advance the state machine. Fix: add `WHERE status = expectedCurrentStatus` to the update or use SERIALIZABLE isolation — broader concurrency model decision (`apps/backend/src/modules/matching/matching.service.ts`).
- No `handyman_id` index on `handyman_location_updates` — composite index covers `(request_id, recorded_at)` but future handyman-scoped queries (auditing, analytics) will full-scan the table. Add `@@index([handymanId])` when growth justifies it (`apps/backend/prisma/migrations/20260518120000_add_handyman_location_updates/migration.sql`).
- Unconditional `refetchInterval: 30_000` in `useActiveJob` — polling continues after job status becomes COMPLETE; generates background 400 errors. Gate on active-lifecycle statuses or stop on terminal status. Revisit when story 4.3 introduces WebSocket push (`apps/frontend/src/features/handyman-active-job/hooks/useActiveJob.ts`).
- `RequestTrackingMap` job pin stuck on initial mount coordinates — `useEffect` with empty `[]` deps means if `jobLat`/`jobLng` are null on first render (loading) the job pin never appears after data loads. Separate a pin-update effect that depends on `[jobLat, jobLng]` (`apps/frontend/src/features/request-tracking/components/RequestTrackingMap.tsx`).
